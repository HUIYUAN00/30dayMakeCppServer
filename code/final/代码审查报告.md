# 最终版（code/final）代码审查报告

- 审查对象：`code/final`（整合后的独立可执行版本）
- 审查方式：源码静态审查 + GCC 13 编译 + 功能测试 + AddressSanitizer + 背压/异常关闭压力测试
- 审查日期：2026-10-20
- 结论：**功能可运行，但当前版本不具备生产可用性**。存在 3 个 P0 级问题，其中 2 个已实际复现（事件回调内 use-after-free、发送缓冲区在 EAGAIN 时丢数据），1 个在 `-DNDEBUG` 发布构建下必现（服务无法启动）。

> **修复状态（2026-10-21）**：P0-1 ~ P0-3、P1-1 ~ P1-6 已全部修复并回归验证通过：

## 2. P0 级问题（优先修复）

### P0-1 事件回调内销毁连接导致 use-after-free

**位置**

- `code/final/src/Channel.cpp:32-38`
- `code/final/src/Connection.cpp:140-164`
- `code/final/src/TcpServer.cpp:76-83`

**问题链路**

1. `Connection::Business()` 检测到 EOF/写错误，把状态置为 `Closed`。
2. 函数末尾调用 `delete_connection_(fd)`，`TcpServer::DeleteConnection()` 从 `connections_` 中 `erase` 该连接。
3. `Connection` 析构 → `Channel` 析构 → 从 epoll 删除。
4. 返回 `Channel::HandleEvent()` 后，第 36 行继续读取 `ready_events_`，此时 `this`（Channel）已被释放。

**ASan 证据**

```text
ERROR: AddressSanitizer: heap-use-after-free
READ of size 2 ... in Channel::HandleEvent() const src/Channel.cpp:36
...
freed by thread T9 here:
    Connection::~Connection() src/Connection.cpp:26
    TcpServer::DeleteConnection(int) src/TcpServer.cpp:82
```

**影响**：随机崩溃、数据损坏，属于内存安全缺陷；即使当前回显场景“看起来正常”，也属于未定义行为。

**建议**

- 正确方案：把连接删除延迟到本轮事件分发之后。给 `EventLoop` 增加任务队列（如 `QueueInLoop(std::function<void()>)`），`Connection::Business()` 只标记关闭并把删除任务入队；`Loop()` 在 `Poll()` 返回的这一批 Channel 全部处理完后再执行删除任务。
- 或者将连接生命周期改为 `std::shared_ptr<Connection>`，事件分发期间持有强引用，回调结束后再释放。
- 不推荐仅“在回调后不访问成员”的补丁式写法：对象在成员函数执行期间被销毁仍然是未定义行为。

### P0-2 发送缓冲在 EAGAIN/部分写时被清空，造成静默丢数据

**位置**

- `code/final/src/Connection.cpp:39-50`
- `code/final/src/Connection.cpp:79-97`

**问题**

`WriteNonBlocking()` 遇到 `EAGAIN/EWOULDBLOCK` 直接 `break`，随后 `Write()` 无条件执行 `send_buf_->Clear()`。内核发送缓冲区满或只写入一部分时，剩余数据被永久丢弃；同时没有注册 `EPOLLOUT` 重试。

**实测证据**

客户端发送 4 MiB 后暂停读取，再恢复读取：

```text
sent=4194304 received=516608 lost=3677696 loss_rate=87.7%
```

回显小报文时不易触发，一旦有慢客户端或大响应就会大量丢数据。

**建议**

- 为连接维护 `send_offset_`，只清理已发送部分；未发完时 `channel_->EnableWrite()`。
- 为 Channel 注册写回调，`EPOLLOUT` 时继续 flush，发完后再移除写关注。
- 使用 `send(..., MSG_NOSIGNAL)` 或在启动时忽略 `SIGPIPE`。
- 增加发送队列高水位与背压策略（超过上限断开或暂停读）。

### P0-3 NDEBUG 发布构建下服务无法启动

**位置**：`code/final/src/Acceptor.cpp:15-17`

```cpp
assert(socket_->Create() == RC_SUCCESS);
assert(socket_->Bind(ip, port) == RC_SUCCESS);
assert(socket_->Listen() == RC_SUCCESS);
```

**问题**：`assert` 在定义 `NDEBUG` 时整个表达式不会被求值，`Create/Bind/Listen` 根本不会执行，`fd_` 保持 `-1`。

**实测证据**

```bash
g++ -std=c++17 -O2 -DNDEBUG -pthread -Iinclude -DOS_LINUX src/*.cpp apps/server.cpp -o /tmp/server_ndebug
/tmp/server_ndebug 12350
# 输出：epoll add error: Bad file descriptor
# 退出码：1
```

**建议**：初始化必须写成显式调用并检查返回值或抛异常，不能放在 `assert` 中：

```cpp
RC rc = socket_->Create();
if (rc != RC_SUCCESS) throw std::runtime_error("socket create failed");
rc = socket_->Bind(ip, port);
if (rc != RC_SUCCESS) throw std::runtime_error("socket bind failed");
rc = socket_->Listen();
if (rc != RC_SUCCESS) throw std::runtime_error("socket listen failed");
```

## 3. P1 级问题

### P1-1 `onConnect` 使用解锁后的裸指针，存在并发 UAF

**位置**：`code/final/src/TcpServer.cpp:62-71`

**问题**：连接插入 map 并解锁后，主线程才执行 `on_connect_(raw_conn)`。此时 sub reactor 已经可以通过 `set_on_recv()` 注册的读事件收到 EOF 并删除连接，`raw_conn` 可能已经悬空。

**建议**

- 在向 sub reactor 注册读事件之前执行 `onConnect`；或
- 连接使用 `shared_ptr`，回调参数改传 `weak_ptr/shared_ptr`；或
- 将 `onConnect` 调用投递到连接所属 EventLoop 中执行。

同时建议把 `on_connect_` 的读取放入锁内获取副本，避免与 `onConnect()` 的动态修改竞争（该配置通常只在启动前设置，但接口未约束）。

### P1-2 未处理 `EPOLLERR / EPOLLHUP / EPOLLRDHUP`

**位置**：`code/final/src/Poller.cpp:49-57`

当前只把 `EPOLLIN` 映射为 `READ_EVENT`、`EPOLLOUT` 映射为 `WRITE_EVENT`。若某次事件只带 `EPOLLERR/EPOLLHUP`（对端 RST、半关闭等），Channel 不会触发任何回调，连接不会被读取、关闭或删除，造成 fd 泄漏，最终耗尽资源。

**建议**

```cpp
if (events & (EPOLLERR | EPOLLHUP | EPOLLRDHUP)) {
  events |= EPOLLIN;  // 交给读回调处理 EOF/错误并关闭
}
```

或在 Channel 增加独立的 `error_callback_`，由连接层读取 `SO_ERROR` 后统一走关闭路径。

### P1-3 未忽略 `SIGPIPE`

**位置**：`code/final/src/Connection.cpp` 的 `write()` 调用、`apps/server.cpp`

向对端已关闭的 socket 写数据时，Linux 默认发送 `SIGPIPE` 并终止进程，而不是返回 `EPIPE`。当前程序没有 `SIG_IGN`，也没有使用 `MSG_NOSIGNAL`。异常关闭压力测试未触发，但这是典型的生产事故源。

**建议**：启动时 `signal(SIGPIPE, SIG_IGN)`，或统一改用 `send(fd, ..., MSG_NOSIGNAL)`。

### P1-4 无消息边界，TCP 粘包/拆包会破坏业务语义

**位置**

- `code/final/src/Connection.cpp:28-32`（每次 `Read()` 前清空读缓冲）
- `code/final/src/Connection.cpp:53-75`（一次事件内读到 EAGAIN 为止）
- `apps/server.cpp` 的 `onRecv` 直接把整个读缓冲当作一条消息

TCP 是字节流：客户端先发 `hel`、再发 `lo`，服务器会分别触发两次 `onRecv`；多个小包也可能合并成一次。当前回显服务问题不明显，但任何真实协议（HTTP、RPC、聊天）都会错误。

**建议**：实现长度字段或分隔符解码循环，保留未消费的半包；为单条消息设置最大长度；`onRecv` 改为“可消费字节流”的语义。

### P1-5 读缓冲、连接数、空闲时间无上限

**位置**：`code/final/src/Connection.cpp:53-75`、`TcpServer` 连接表

- ET 模式下循环读取直到 EAGAIN，恶意客户端可持续发送，`read_buf_` 无限增长。
- 没有最大连接数、空闲超时、单 IP 限制。

**建议**：设置读缓冲高水位（如 1 MiB）与单帧上限；超限关闭并记录；增加空闲连接定时器、最大连接数和 accept 限流。

### P1-6 阻塞 accept 与失败处理不足

**位置**：`code/final/src/Acceptor.cpp:29-40`

监听 fd 未设为非阻塞，且每次可读只 `accept` 一次。`accept` 失败（如 `EMFILE`）后监听 fd 仍处于可读状态，水平触发会不断回调，形成 100% CPU 忙循环；阻塞 `accept` 也可能在罕见情况下卡住事件循环。

**建议**：监听 fd 设为非阻塞；`accept` 循环直到 `EAGAIN`；区分 `EINTR/EMFILE/ENFILE`，对 fd 耗尽做退避或预留空闲 fd 的处理。

## 5. P3 级与工程优化建议

1. **二进制接口**：`Buffer::set_buf(const char*)` 以 C 字符串构造，遇到 `\0` 会截断；应优先使用 `set_buf(const std::string&)`，或提供指针+长度接口。
2. **地址解析**：`inet_addr()` 已过时且无法区分非法地址与 `INADDR_NONE`，建议改用 `inet_pton()` 并校验端口范围。
3. **IPv6/双栈**：当前仅 IPv4；如需对外服务应支持 `AF_INET6` 与 `IPV6_V6ONLY` 配置。
4. **TCP 选项**：按场景设置 `TCP_NODELAY`、`SO_KEEPALIVE`、`TCP_KEEPIDLE` 等。
5. **日志**：多线程直接 `std::cout` 会交错输出，且无级别/时间/连接标识；建议引入异步 logger 或至少加锁封装。
6. **异常安全**：`ThreadPool` 丢弃 `future`，任务异常被吞掉；回调抛出异常会终止 reactor 线程。建议统一捕获并记录。
7. **错误码体系**：`RC` 过粗，连接层无法区分“暂时错误/永久错误/对端关闭”，建议细分并携带 `errno`。
8. **优雅关闭**：当前 Stop 后直接关闭连接；可先 `shutdown(SHUT_WR)`，等待发送队列清空或超时再关闭，减少 RST。
9. **没有 HTTP/TLS**：README 中 HTTP 仍是 TODO；对外部署必须在前面加 TLS 终止与反向代理。
10. **文档与接口约束**：线程模型、回调线程归属、连接生命周期、消息边界语义应在头文件注释中明确。

## 7. 回归验证建议

修复后至少覆盖以下用例：

- 回显：小报文、中文、二进制、1 KiB ~ 10 MiB。
- 并发：100+ 连接同时收发；连接建立/关闭风暴。
- 异常关闭：发送后立即 `close`、`SO_LINGER=0` 触发 RST、半关闭。
- 背压：客户端只发不收/只收不发，校验无丢数据且内存有上限。
- 协议：拆包（分多次写）、粘包（一次写多条消息）。
- 资源：连续 10k 连接后检查 fd 数、RSS、连接表大小。
- 退出：`SIGINT/SIGTERM` 下活跃连接、空闲连接、正在发送数据三种状态都能退出。
- 工具：ASan + UBSan 全量用例；TSan 覆盖连接建立/删除路径。
